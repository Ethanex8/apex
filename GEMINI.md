# Apex Engineering & Couch-to-Silicon Platform Invariants

## 1. Zero-Throwaway Hardware Convergence
- **One Cohesive Machine**: Every subsystem (`brain`, `drive`, `power`, `limb`, `walker`, `sight`) must function as a verifiable standalone desktop build *and* bolt directly into the final `~2.5 kg` autonomous quadruped without circuit-board redesigns (`respins`) or throwaway subsystems.
- **Locked Interface Contracts**: All electrical rails (`21.9V` max 6-cell `LiFePO4` touch-safe Extra-Low Voltage / `SELV` bus, regulated `5V`/`3.3V` logic rails), communication frames (dual `5 Mbps` noise-immune differential motor bus / `CAN-FD`, `sight <-> brain` framed velocity link, sub-microsecond programmable-chip camera sync pulse), and mechanical mounting patterns are canonically specified in `VISION.md` and `systems/*/README.md`.
- **Home-Safe by Design**: Physical hardware targets `~2.5 kg` total mass, `< 22V` touch-safe lithium-iron-phosphate (`LiFePO4`) power, `< 2.5 N·m` hand-backdrivable joints, current-limited bench power-supply (`PSU`) bring-up before connecting batteries, physical mushroom emergency-stop (`E-stop`) cutoffs, and factory-assembled boards/parts (`turnkey PCBA`, industrial powder-fused nylon `MJF`, and `CNC` milling) to avoid indoor solder-paste or high-temp plastic fumes.

## 2. Textbook-Style Writing for General Programmers & Aspiring Engineers (High Rigor, Zero Unexplained Jargon)
- **Reader Persona**: Write like a classic systems engineering textbook (*Harris & Harris*, *Crafting Interpreters*, *Hennessy & Patterson*) aimed at **an engineer or aspiring engineer who knows general programming plus undergraduate math and physics, does not instantly remember every specialist topic, and has zero prior background in computer architecture/ISAs (like RISC-V), chip-design/EDA toolchains, electrical circuits, or mechanical shop jargon**. Never dumb down equations or physics, never assume familiarity with *any* hardware acronym, mnemonic, vendor name, or shorthand, and **never anchor explanations in niche software specialties** (such as lock-free database engines, write-ahead logs, distributed consensus, OS-kernel demand paging, or JVM internals)—bridge instead from everyday programming (`if`/`else`, arrays, loops, functions, structs, byte buffers) and gently refresh any specialized math before using formal notation.
- **Mechanism First, Immediate Adjacency (`No Acronym Soup`)**: Whenever *any* domain term, instruction mnemonic, register name, memory technology, tool/vendor name, or testing term appears for the first time, state **what it does in plain everyday language first** and place its **expanded name / acronym immediately adjacent** to the noun phrase it defines—e.g., *"hardware selector switches (**multiplexers**), the circuit equivalent of `cond ? a : b`"*, or *"a 16 MB soldered-on persistent storage chip (**Quad Serial Peripheral Interface / QSPI Flash**)"*—never separated by a parenthetical or em-dash clause, and never stacking 3+ new acronyms in one sentence.
- **General Principles Before Project Constants & Self-Explanatory Visuals**: Never drop project-specific constants (such as a `50 MHz` board clock or `"48 -> 128 -> 128 -> 12"` network widths) into general conceptual explanations where the underlying principle holds at any rate or size, and ground every system constant physically when its subsystem is introduced. In interactive visualizers (`generative_ui` and Vue `.hw-widget` figures) and diagrams, spell out mnemonics, align bit-slice labels to actual bit positions (`Bits 31..25`, never cryptic datasheet shorthand like `imm[12|10:5]`), and never mutate state without visibly showing where inputs came from.
- **Concise Headings, Zero Front-Matter Banners & Semantic Line Breaks**: Keep chapter H1 titles (`<= 6` words) and `##`/`###` section headings (`<= 8` words) crisp and focused on the primary topic without `&`, `Hook: Subtitle` colons, or parenthetical clutter. Open chapters directly with introductory prose—never add front-matter blockquotes (`Part I · Reading Time`, `Primary Modules`, `Interactive Figures`). Write Markdown prose as **one sentence per line** (single newlines, never trailing two-space `<br>` breaks) so GitHub PR reviewers can comment on any individual sentence cleanly.
- **Code-Only Backticks, Restrained Boldface & Math Hygiene**: Reserve inline backticks strictly for literal code identifiers, machine instructions/registers (`x0`, `add`, `lw`, `self.pc`), hex/binary literals (`0x8000_0000`), CLI flags, and file paths—never wrap English acronyms (HDL, ISA, ALU, FPGA, MMIO, CSR), language/architecture/tool proper nouns (SystemVerilog, RISC-V, RV32I, Verilator, Python), prose numbers/units (`32-bit`, `50 MHz`, `32 wires`), or raw LaTeX (`Z_{2^N}`) in backticks. Reserve boldface (`**...**`) for newly defined technical terms (`<= 6` words) and bullet lead-ins, never rhetorical phrases. Reserve `$...$` for math, escape literal currency (`\$`) in prose, and write *"about"* or *"roughly"* instead of `~` in prose.
- **Directness, Zero Meta-Commentary & Engineering Naming**: Introduce every subsystem, module, and mechanism directly by what it **is** and **does**—never open with meta-commentary about curricula, reader transitions, or negative foils. Use plain-English subsystem IDs (`brain`, `drive`, `power`, `limb`, `walker`, `sight`) and sequential step IDs (`<system>-NN`).

## 3. Declarative Single Source of Truth (`roadmap.yaml` & `scripts/build.py`)
- **Canonical Roadmap & Textbook Outline**: `roadmap.yaml` is the single source of truth for all 6 systems, phases, 186 atomic `couch` and `bench` steps, verification commands, first-principles concepts, home-workbench procurement gates, step completion state (`pending`, `in_review`, `approved`), and the 8-part, 34-chapter companion book syllabus (`book.parts`).
- **Automated Compilation & Validation**: Never hand-edit `ROADMAP.md` or `README.md` directly. After modifying `roadmap.yaml` (directly or via `scripts/step.py`), always run `python3 scripts/build.py` to validate all schema, dependency-graph (`DAG`), book-partition, and step-completeness invariants and regenerate `ROADMAP.md` and `README.md`, then confirm zero drift with `python3 scripts/build.py --check`.

## 4. Couch-to-Silicon Atomic Review Contract & Iterative Open-PR Loop
- **Strictly One Step at a Time**: Agents execute at most one atomic step from `roadmap.yaml` per turn (`~50–150 LOC` for software or hardware-description code steps, or one bounded circuit-board/3D-CAD milestone). Never bundle multiple steps together.
- **4-Pass Technical Artifact Pipeline & Strict Verification**: Every Python, Shell, SystemVerilog, and C/Header artifact (`scripts/` and `systems/`) must be authored via the **4-Pass Artifact Pipeline** (`apex-artifact-author`: Architecture & `<= 80`-LOC Modularity Blueprint -> Self-Documenting Contracts & 100% Docstrings -> Isolated `research` Staff-Engineer Audit -> `python3 scripts/check_code.py` + `>= 95%` test coverage / `Verilator` / `Yosys` / `nextpnr` / `KiCad` / `MuJoCo` verification) before entering `in_review`.
- **Cohesive Multi-Step Textbook Chapters (`systems/<system>/chapters/<NN>_<slug>.md` + `book/`)**: The companion textbook on GitHub Pages (`https://ethanex8.github.io/apex/`) is organized chronologically into **8 discipline-based Parts and 34 cohesive Chapters** defined in `roadmap.yaml` (`book.parts`), decoupled `M:1` from atomic PR steps. The first `couch` step mapped to a chapter drafts its opening sections (`about 15–25 minutes`); subsequent `couch` steps extend that chapter with `1–2` focused sections (`about 10–20 minutes` per PR, converging to `about 45–60 minutes` per completed chapter) before *Graded Engineering Exercises*; and experimental `bench` steps populate a closing *Hardware Lab* section once physical measurements return (pure order-placement steps add concise fabrication callouts only). Chapters are authored via the **4-Pass Textbook Pipeline** (`apex-textbook-author`: Blueprint -> Multi-Chunk First-Principles Draft with `<!-- book-sync: <spec> -->` and `<<< @/systems/...#Lstart-Lend` live transclusions -> 3-Specialist Parallel Cold-Reader Audit with Re-Review Convergence -> Interactive Vue Hardware Widgets + Graded Exercises with collapsible worked solutions) and must pass `python3 scripts/sync_book.py --check`, `python3 scripts/check_book.py`, `python3 scripts/build.py --check`, `BOOK_BASE=/apex/ npm --prefix book run build`, and `uv run --with playwright python3 scripts/check_visuals.py`. Every concept and code/test symbol link must anchor directly to exact lines/functions via AST/parser symbols (`#Lstart-Lend`, never polluting source files with `#region` markers).
- **Iterative Open-PR Review Loop, Self-Healing Feedback & Hard Approval Gate**: Keep the review/step PR **OPEN** across as many user-feedback -> `apex-skill-healer` -> fix -> fast-forward commit/push cycles as needed until explicit final user approval (`LGTM`)—never close/merge a PR prematurely and never force-push away reviewed commits so GitHub's inline comment threads and *"Changes since last review"* stay intact. Whenever user review comments arrive, invoke `apex-skill-healer` (syncing any updated `.agents/skills/*` to the active skill registry via `save_skill`) before patching deliverable files. Keep in-chat review packets concise and mobile-friendly (Plain-English Overview + live GitHub Pages link, Visual Preview, Guided Diff Tour + Verification summary; zero multi-question Socratic quiz walls), and wait for explicit final `LGTM` before running `python3 scripts/step.py approve <step-id>` and merging/cleaning up review branches.
