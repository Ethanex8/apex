# Apex Engineering & Couch-to-Silicon Platform Invariants

## 1. Zero-Throwaway Hardware Convergence
- **One Cohesive Machine**: Every subsystem (`brain`, `drive`, `power`, `limb`, `walker`, `sight`) must function as a verifiable standalone desktop build *and* bolt directly into the final `~2.5 kg` autonomous quadruped without circuit-board redesigns (`respins`) or throwaway subsystems.
- **Locked Interface Contracts**: All electrical rails (`21.9V` max 6-cell `LiFePO4` touch-safe Extra-Low Voltage / `SELV` bus, regulated `5V`/`3.3V` logic rails), communication frames (dual `5 Mbps` noise-immune differential motor bus / `CAN-FD`, `sight <-> brain` framed velocity link, sub-microsecond programmable-chip camera sync pulse), and mechanical mounting patterns are canonically specified in `VISION.md` and `systems/*/README.md`.
- **Home-Safe by Design**: Physical hardware targets `~2.5 kg` total mass, `< 22V` touch-safe lithium-iron-phosphate (`LiFePO4`) power, `< 2.5 N·m` hand-backdrivable joints, current-limited bench power-supply (`PSU`) bring-up before connecting batteries, physical mushroom emergency-stop (`E-stop`) cutoffs, and factory-assembled boards/parts (`turnkey PCBA`, industrial powder-fused nylon `MJF`, and `CNC` milling) to avoid indoor solder-paste or high-temp plastic fumes.

## 2. Textbook-Style Writing for General Programmers & Aspiring Engineers (High Rigor, Zero Unexplained Jargon)
- **Reader Persona**: Write like a classic systems engineering textbook (*Harris & Harris*, *Crafting Interpreters*, *Hennessy & Patterson*) aimed at **an engineer or aspiring engineer who knows general programming plus undergraduate math and physics, does not instantly remember every specialist topic, and has zero prior background in computer architecture, chip-design toolchains, electrical circuits, or mechanical shop jargon**. Never dumb down equations or physics, never assume familiarity with *any* hardware acronym, mnemonic, vendor name, or shorthand, and **never anchor explanations in niche software specialties** (such as database internals, distributed consensus, kernel demand paging, or managed runtime internals)—bridge instead from everyday programming (`if`/`else`, arrays, loops, functions, structs, byte buffers) and gently refresh any specialized math before using formal notation.
- **Mechanism First, Immediate Adjacency (`No Acronym Soup`)**: Whenever *any* domain term, instruction token, register name, memory technology, tool/vendor name, or testing term appears for the first time, state **what it does in plain everyday language first** and place its **expanded name / acronym immediately adjacent** to the noun phrase it defines—never separated by a parenthetical or em-dash clause, and never stacking 3+ new acronyms in one sentence.
- **General Principles, Abstraction Boundaries & Self-Explanatory Visuals**: Never drop project-specific sizing or clock constants into general conceptual explanations where the underlying principle holds at any scale or rate, and ground every system constant physically when its subsystem is introduced. Explain higher-layer architectural behavior strictly in terms of that layer's contract—never leak unintroduced lower-layer ports, pins, or circuit mechanisms before those lower layers are built. Lead comparative sections with a direct plain-English takeaway and justify implementation choices honestly without unmotivated slogans. In interactive visualizers (`generative_ui` and Vue `.hw-widget` figures) and diagrams, spell out tokens, align bit-slice labels to explicit bit positions (`Bits hi..lo`, never cryptic datasheet shorthand), audit widgets at their exact insertion line so they preview no later code or symbols, and never mutate state without visibly showing where inputs came from.
- **Concise Headings, Zero Front-Matter Banners & Semantic Line Breaks**: Keep chapter H1 titles (`<= 6` words) and `##`/`###` section headings (`<= 8` words, closing with `## <N>. Exercises`) crisp and focused on the primary topic without `&`, `Hook: Subtitle` colons, or parenthetical clutter. Open chapters directly with introductory prose—never add front-matter blockquotes or figure-inventory banners—and open every `##`/`###` subsection with a calm 2–4 sentence conceptual bridge while keeping subsection content strictly aligned to its heading. Write Markdown prose as **one sentence per line** (single newlines, never trailing two-space `<br>` breaks) so GitHub PR reviewers can comment on any individual sentence cleanly.
- **Code-Only Backticks, Restrained Boldface & Math Hygiene**: Reserve inline backticks strictly for literal code identifiers, machine instruction/register tokens, literal constants, CLI flags, and file paths—never wrap English acronyms, language/architecture/tool proper nouns, prose numbers/units, or raw LaTeX in backticks. Reserve boldface (`**...**`) for newly defined technical terms (`<= 6` words) and bullet lead-ins, never rhetorical phrases. Reserve `$...$` for math, escape literal currency (`\$`) in prose, and write *"about"* or *"roughly"* instead of `~` in prose.
- **Proof Rigor, Lemma Order & Step-by-Step Display Algebra**: Derive every mathematical or bitwise equivalence claim *and* every claimed exception/contrast in strict dependency order without forward corollary citations. Refresh prerequisite undergraduate math or physics identities with a concise derivation and example before use, define every operator before bounding corner cases, justify chosen representations and transfer shared results via established equivalence instead of repeating redundant parallel proofs, and explicitly prove non-obvious rounding directions. Never describe sub-terms, indices, or exponents of an equation before that equation appears, and motivate every algebraic precondition by explicitly stating which step or theorem requirement depends on it. Keep motivating sentences focused on one primary reason (unpacking caveats or uniqueness justifications in separate plain sentences), promote in-paragraph or wordy mathematical narration into compact aligned display equations expanding each algebraic step cleanly, ensure intro prose matches the exact operations displayed below, and verify every causal connective (*because*, *consequently*, *therefore*, *thus*) follows directly from its premise.
- **Logical Macro/Micro Ordering & Base-Before-Extension Layering**: Complete self-contained base architectures before custom domain extensions, co-locate specialized helpers with the subsystem that motivates them rather than front-loading them early, never braid two separate mechanisms or theorems inside one paragraph or numbered list item (introduce each new operation with plain-English intuition and its own motivating example before entering boundary cases or formal equations), and place foundational lemmas immediately after their motivating definitions.
- **Tables & Lists Over Enumerative Prose, Balanced End-to-End Rigor**: Present any 3+ parallel items sharing structured attributes (encoding comparisons, bit-slice maps, instruction catalogs, register maps, interrupt bit alignments, fault rules) in scannable Markdown tables or structured lists rather than multi-clause prose walls. Distribute mathematical and quantitative engineering derivations evenly across *all* sections—avoiding pedantic degenerate-case detours early and never letting later sections drop into flat helper/datasheet narration.
- **Directness, Zero Meta-Commentary & Engineering Naming**: Introduce every subsystem, module, and mechanism directly by what it **is** and **does**—never open with meta-commentary about curricula, reader transitions, or negative foils. Use plain-English subsystem IDs (`brain`, `drive`, `power`, `limb`, `walker`, `sight`) and sequential step IDs (`<system>-NN`).

## 3. Declarative Single Source of Truth (`roadmap.yaml` & `scripts/build.py`)
- **Canonical Roadmap & Textbook Outline**: `roadmap.yaml` is the single source of truth for all 6 systems, phases, 186 atomic `couch` and `bench` steps, verification commands, first-principles concepts, home-workbench procurement gates, step completion state (`pending`, `in_review`, `approved`), and the 8-part, 34-chapter companion book syllabus (`book.parts`).
- **Automated Compilation & Validation**: Never hand-edit `ROADMAP.md` or `README.md` directly. After modifying `roadmap.yaml` (directly or via `scripts/step.py`), always run `python3 scripts/build.py` to validate all schema, dependency-graph (`DAG`), book-partition, and step-completeness invariants and regenerate `ROADMAP.md` and `README.md`, then confirm zero drift with `python3 scripts/build.py --check`.

## 4. Couch-to-Silicon Atomic Review Contract & Iterative Open-PR Loop
- **Strictly One Step at a Time**: Agents execute at most one atomic step from `roadmap.yaml` per turn (`~50–150 LOC` for software or hardware-description code steps, or one bounded circuit-board/3D-CAD milestone). Never bundle multiple steps together.
- **4-Pass Technical Artifact Pipeline & Strict Verification**: Every Python, Shell, SystemVerilog, and C/Header artifact (`scripts/` and `systems/`) must be authored via the **4-Pass Artifact Pipeline** (`apex-artifact-author`: Architecture & `<= 80`-LOC Modularity Blueprint -> Self-Documenting Contracts & 100% Docstrings -> Isolated `research` Staff-Engineer Audit -> `python3 scripts/check_code.py` + `>= 95%` test coverage / `Verilator` / `Yosys` / `nextpnr` / `KiCad` / `MuJoCo` verification) before entering `in_review`.
- **Cohesive Multi-Step Textbook Chapters (`systems/<system>/chapters/<NN>_<slug>.md` + `book/`)**: The companion textbook on GitHub Pages (`https://ethanex8.github.io/apex/`) is organized chronologically into **8 discipline-based Parts and 34 cohesive Chapters** defined in `roadmap.yaml` (`book.parts`), decoupled `M:1` from atomic PR steps. The first `couch` step mapped to a chapter drafts its opening sections (`about 15–25 minutes`); subsequent `couch` steps extend that chapter with `1–2` focused sections (`about 10–20 minutes` per PR, converging to `about 45–60 minutes` per completed chapter) before `## <N>. Exercises`; and experimental `bench` steps populate a closing *Hardware Lab* section once physical measurements return (pure order-placement steps add concise fabrication callouts only). Chapters are authored via the **4-Pass Textbook Pipeline** (`apex-textbook-author`: Blueprint -> Multi-Chunk First-Principles Draft with `<!-- book-sync: <spec> -->` and `<<< @/systems/...#Lstart-Lend` live transclusions -> 3-Specialist Parallel Cold-Reader Audit with Re-Review Convergence -> Interactive Vue Hardware Widgets + `## <N>. Exercises` with collapsible worked solutions) and must pass `python3 scripts/sync_book.py --check`, `python3 scripts/check_book.py`, `python3 scripts/build.py --check`, `BOOK_BASE=/apex/ npm --prefix book run build`, and `uv run --with playwright python3 scripts/check_visuals.py`. Every concept and code/test symbol link must anchor directly to exact lines/functions via AST/parser symbols (`#Lstart-Lend`, never polluting source files with `#region` markers).
- **Iterative Open-PR Review Loop (4-Step Subset Recall) & Hard Approval Gate**: Always open human review PRs **Ready for Review** immediately (never `--draft`), and keep the PR **OPEN** across as many user-feedback -> `apex-skill-healer` -> fix -> fast-forward commit/push cycles as needed until explicit final user approval (`LGTM`)—never close/merge a PR prematurely and never force-push away reviewed commits so GitHub's inline comment threads and *"Changes since last review"* stay intact. Whenever user review comments arrive, follow the 4-step protocol in `docs/REVIEW_PROCESS.md` and `apex-skill-healer` (Step 1 triage + anti-cheating persona-diff artifact at Gate 1 -> Step 2 isolated panel subset-match loop with conditional Gate 2 -> Step 3 clean-room deliverable convergence + `calibration_log.md` -> Step 4 fast-forward push, inline thread replies via `gh api .../pulls/<N>/comments/<id>/replies`, resolving answered threads, and book deploy). Keep in-chat review packets concise and mobile-friendly (Plain-English Overview + live GitHub Pages link, Visual Preview, Guided Diff Tour + Verification summary; zero multi-question Socratic quiz walls), and wait for explicit final `LGTM` before running `python3 scripts/step.py approve <step-id>` and merging/cleaning up review branches.
